## Как устроено решение

Основная логика находится в `app/service.py`. HTTP API, исходные товары и задержка источника остаются заданными каркасом.

- **Cache-aside.** GET проверяет Redis. При свежей корректной записи возвращает товар без обращения к источнику. Промах, повреждённая запись или истечение срока приводят к чтению источника и заполнению кэша.
- **Формат и срок.** JSON содержит `product`, `fresh_until` и `expires_at` и проверяется Pydantic. Значение и конечный TTL записываются одной операцией `SET ... PX`. Миллисекунды округляются вверх; точную границу срока дополнительно проверяет переданная функция `clock()`. При `now == expires_at` запись уже просрочена.
- **PATCH.** Сначала обновляется источник, затем удаляется только ключ изменённого товара. После успешного PATCH следующий GET не должен возвращать предыдущую версию.
- **Сбой Redis.** Ошибки GET/SET/DEL не делают исправный источник недоступным. Если после обновления источника инвалидация не подтверждена, ключ остаётся в локальном множестве `dirty`: чтение старой записи запрещено. Метка ставится до `await DEL`, поэтому отмена запроса в этой точке также не возвращает доверие к старому кэшу. Последующие GET повторяют удаление и/или записывают свежий результат; доверие восстанавливается после успешной операции. Другие товары продолжают использовать кэш.
- **Конкурентность.** Для каждого товара есть отдельная `asyncio.Lock`. Промахи повторно проверяют кэш внутри неё: первый запрос загружает товар, остальные используют результат. Та же блокировка согласует заполнение, PATCH и фоновое обновление. Свежие и допустимо устаревшие попадания не ждут её. `WeakValueDictionary` позволяет не хранить уже не используемые блокировки бессрочно; пока блокировка используется или ожидается, её удерживают сильные ссылки.
- **SWR.** До `fresh_until` запись свежая; между `fresh_until` и `expires_at` она немедленно возвращается, а обновление запускается в фоне. После `expires_at` нужен результат источника. Одновременно выполняется не больше одной фоновой задачи на товар. Callback удаляет из реестра только ту задачу, к которой относится. Ошибка обновления логируется и не продлевает срок старых данных. `wait_idle()` ожидает задачи, `aclose()` отменяет и собирает их результаты.

В cache-aside полный TTL равен `fresh_ttl`, в SWR — `fresh_ttl + stale_ttl`. Блокировки и `dirty` действуют в одном процессе, одном event loop и одном экземпляре сервиса, как предусмотрено [заданием](ASSIGNMENT.md). Для нескольких процессов понадобился бы отдельный протокол координации. Ошибки основного источника не превращаются в успешный ответ; ошибка фонового обновления наблюдаема в логах, а выдача stale ограничена исходным сроком.

## Вопросы для защиты

| Вопрос | Короткий ответ |
|---|---|
| Зачем TTL и в Redis, и в JSON? | Redis удаляет запись физически. Метки позволяют проверять свежесть через `clock()`, различать два интервала SWR и воспроизводить границы времени в тестах. |
| Почему `SET PX`, а не отдельный `EXPIRE`? | Между двумя командами процесс может прерваться и оставить бессрочный ключ. Одна команда атомарно задаёт значение и срок. |
| Зачем повторная проверка внутри lock? | Пока запрос ждал блокировку, другой запрос мог уже заполнить кэш. Без повторной проверки все ожидающие снова читали бы источник. |
| Почему не одна общая блокировка? | Медленное чтение товара 1 не должно задерживать товар 2. |
| Почему PATCH сначала меняет источник? | Если удалить кэш до записи источника, конкурентный GET может снова сохранить старый товар. Дополнительно заполнение и PATCH согласованы одной блокировкой товара. |
| Что будет при неудачном DEL? | Источник уже изменён, но старый ключ мог сохраниться. Локальная метка `dirty` запрещает его использовать до подтверждённого восстановления. |
| Что будет при отмене PATCH во время DEL? | Метка уже выставлена. Следующий GET не доверится старой записи, а блокировка освободится при выходе из контекстного менеджера. |
| Может ли старый refresh затереть PATCH? | Refresh и PATCH используют одну блокировку. Если refresh начался первым, PATCH дождётся его и затем инвалидирует результат. Если PATCH был первым, обновление читает уже новое состояние. |
| Почему stale-читатель не берёт lock? | Иначе он ждал бы медленный refresh и терял бы главное свойство SWR — быстрый ответ в разрешённом интервале. |
| Что если refresh завершился ошибкой? | Ошибка попадает в лог, запись не получает новый срок. Следующее stale-чтение может повторить обновление; после жёсткого срока нужны свежие данные либо ошибка источника. |
| Что доказывают 20 конкурентных запросов? | Для одного холодного ключа при работающем Redis достаточно одного чтения источника. Это не гарантия ограничения общей нагрузки во время отказа Redis. |
| Подойдёт ли SWR для финальной цены заказа? | Для карточки товара допустимо ограниченное устаревание. Финальную цену и остаток при оформлении заказа нужно перепроверять в основном источнике. |
| Чем полезны собственные тесты? | Они проверяют точные дробные границы TTL, отсутствие refresh для fresh, восстановление после ошибки refresh, независимость ключей при неудачном DEL, отмену PATCH и гонку холодного заполнения с записью в обоих режимах. В файле восемь функций и девять параметризованных случаев. |

## Подготовка записи

Ниже команды для **PowerShell** из корня `redis-cache-lab`. Установку и сборку выполнить до начала записи. Открыть рядом `app/service.py`, `tests/test_expert.py`, `tests/test_additional.py` и отчёт. Увеличить шрифт терминала.

```powershell
$env:CACHE_MODE = 'cache_aside'
$env:FRESH_TTL = '60'
$env:STALE_TTL = '10'
$env:SOURCE_DELAY = '0.1'
$env:API_PORT = '8000'
docker compose up --build -d --force-recreate api
Invoke-RestMethod 'http://localhost:8000/health'
```

Дождаться доступности `/health`. Повышенный TTL даёт время спокойно показать два последовательных запроса; задержка источника остаётся штатной. Тесты создают собственные сервисы со своими TTL и не зависят от демонстрационного режима API.

До записи выполнить полную проверку и собственные тесты; сохранить фактический вывод для отчёта:

```powershell
docker compose run --build --rm tests
docker compose run --build --rm tests python -m pytest -q tests/test_additional.py
```

Для чистой демонстрации после подготовительных GET пересоздать API и дождаться `/health`. Это обнулит учебный источник и создаст новый префикс кэша. Во время самой последовательности GET → PATCH → GET API не перезапускать.

### 0:40–1:25 — GET, счётчик и PATCH

Выполнить блок целиком, чтобы уложиться в TTL:

```powershell
$api = 'http://localhost:8000'
$before = (Invoke-RestMethod "$api/debug/stats").source_reads
$first = Invoke-RestMethod "$api/products/1"
$second = Invoke-RestMethod "$api/products/1"
$after = (Invoke-RestMethod "$api/debug/stats").source_reads
[pscustomobject]@{
    first_revision = $first.revision
    second_revision = $second.revision
    source_reads_delta = $after - $before
} | Format-List
$patched = Invoke-RestMethod "$api/products/1" -Method Patch -ContentType 'application/json' -Body '{"price_kopecks":61000}'
$readback = Invoke-RestMethod "$api/products/1"
[pscustomobject]@{
    patch_price = $patched.price_kopecks
    get_price = $readback.price_kopecks
    patch_revision = $patched.revision
    get_revision = $readback.revision
} | Format-List
```

> Два GET возвращают одну версию. Изменение счётчика source_reads видно на экране: повторный запрос использует кэш. Теперь меняю цену на 61 тысячу копеек. Следующий GET возвращает цену и версию из ответа PATCH — старая запись больше не используется.

### 1:25–2:00 — 20 одновременных холодных GET

Товар 2 до этого не запрашивать. Скрипт обращается к запущенному API из его контейнера, печатает реальные счётчики и проверяет результат:

```powershell
@'
import asyncio
import httpx

async def main():
    async with httpx.AsyncClient(base_url="http://127.0.0.1:8000", timeout=10) as client:
        before_response = await client.get("/debug/stats")
        before_response.raise_for_status()
        before = before_response.json()["source_reads"]
        replies = await asyncio.gather(*(client.get("/products/2") for _ in range(20)))
        for reply in replies:
            reply.raise_for_status()
        after_response = await client.get("/debug/stats")
        after_response.raise_for_status()
        delta = after_response.json()["source_reads"] - before
        print({"requests": len(replies), "source_reads_delta": delta,
               "revisions": sorted({reply.json()["revision"] for reply in replies})})
        assert all(reply.json()["id"] == 2 for reply in replies)
        assert delta == 1, "Expected one source read for a cold key"

asyncio.run(main())
'@ | docker compose exec -T api python -
```

> Здесь двадцать одновременных запросов ещё не прогретого товара. На экране фактический прирост чтений источника. Все запросы получают товар, а первая загрузка заполняет кэш для остальных. Блокировка относится только к этому ключу.

### 2:55–3:40 — границы решения и итог

На экране: `aclose()`, реестр refresh-задач, собственные тесты и заполненный отчёт.

> На один товар запускается одна фоновая задача. Её ошибка логируется и не продлевает допустимый срок старых данных. При остановке фоновые задачи отменяются и ожидаются. Собственные тесты добавляют точные дробные границы TTL, отмену PATCH во время удаления и гонку заполнения с записью. Гарантии ограничены одним процессом и event loop; для нескольких процессов локальной блокировки недостаточно. SWR подходит для карточки товара, а финальные цену и остаток заказа нужно проверить в источнике. Результаты и ограничения перечислены в отчёте.
