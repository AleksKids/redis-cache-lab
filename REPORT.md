Число чтений в последовательной серии снизилось в 20 раз. Время приведено как наблюдение одного локального прогона, не как универсальная гарантия скорости.

В HTTP-опыте SWR источник не менялся: опыт показывает быстрый stale-ответ и дополнительную загрузку. Получение **нового остатка** после фонового обновления отдельно доказывает исходный детерминированный тест E1; гонку с PATCH — E3.

Redis запускается без persistence, поэтому при настоящем stop/start его ключи исчезают. Этот опыт подтверждает доступность API. Сценарий сохранённого старого ключа при сетевом сбое отдельно проверяет B5 через FaultyRedis поверх настоящего Redis.

### Воспроизведение измерений

Пример для PowerShell:

```powershell
$env:CACHE_MODE = 'cache_aside'
$env:FRESH_TTL = '60'
$env:SOURCE_DELAY = '0.1'
docker compose up -d --force-recreate api
docker compose exec -T api python scripts/measure.py sequential --ttl 60
```

Перед каждым следующим опытом повторить `up -d --force-recreate api`. Для конкурентного опыта заменить `sequential` на `concurrent`, для PATCH — на `patch`. Для `expiry` задать `FRESH_TTL=1` и `--ttl 1`. Для `swr` задать `CACHE_MODE=swr`, `FRESH_TTL=1`, `STALE_TTL=5` и `--ttl 1`.

Для реального отказа Redis: пересоздать API в cache-aside с TTL 60 и выполнить `python scripts/check_outage.py` на хосте из корня репозитория. Скрипт останавливает только Redis этого Compose-проекта, делает GET/PATCH и обязательно запускает Redis в `finally`.

Исходное измерение уже сохранено до изменения `service.py`. Для его повторения нужна отдельная копия исходного коммита с теми же настройками и серией из 20 GET; запуск готового решения не воспроизводит исходную заготовку.

## Решения и гарантии

1. **Формат и TTL.** JSON содержит товар, `fresh_until` и `expires_at`; проверяется Pydantic, включая конечность временных меток и соответствие ID ключу. В cache-aside полный срок равен fresh TTL, в SWR — сумме fresh и stale. `SET PX` атомарно сохраняет данные и срок; дробные секунды округляются вверх до миллисекунд. Точная логическая граница проверяется через переданный `clock()`: равенство сроку уже означает истечение.
2. **Изменение товара.** Одна блокировка товара охватывает `source.update → DEL`, а также `source.get → SET` и refresh. Удаляется только `{prefix}:product:{id}`. Нулевая цена и остаток допустимы.
3. **Ошибки Redis.** GET превращается в промах; ошибка SET не мешает вернуть полученный из источника товар; ошибка DEL оставляет ключ недоверенным. Перехватываются ошибки Redis, а не все ошибки программы. Ошибка источника в обычном запросе передаётся вызывающему.
4. **Восстановление.** До ожидания DEL товар помечается `dirty`; отмена запроса тоже сохраняет эту метку. Старое содержимое такого ключа не читается. Следующий запрос повторяет удаление; успешный DEL либо успешный SET свежего снимка восстанавливает доверие. Компромисс: метка локальна, а при сбое возможны дополнительные обращения к Redis и источнику. Другие товары не теряют кэш.
5. **Согласованность.** GET, начавшийся после завершившегося PATCH, видит обновлённый товар. Пересекающийся с PATCH запрос может получить предыдущий снимок. Внешние изменения источника становятся видны после обновления кэша. Длинный TTL уменьшает нагрузку, но увеличивает допустимое время незаметного внешнего изменения.
6. **Конкурентность.** После входа в per-key lock кэш проверяется повторно. При доступном Redis ожидающие запросы используют результат первой загрузки; другой товар имеет свой lock. WeakValueDictionary освобождает неиспользуемые блокировки, активные удерживаются контекстами и ожидающими корутинами. Отмена запроса освобождает lock. Во время сбоя Redis ограничение числа чтений источника не обещается.
7. **SWR и задачи.** Свежие и допустимо устаревшие попадания обслуживаются без ожидания refresh-lock. На ключ хранится одна фоновая задача; callback проверяет её идентичность, чтобы не удалить новую. Ошибка refresh логируется и не продлевает hard expiry. `wait_idle()` ожидает снимок запущенных задач; `aclose()` запрещает новые refresh, отменяет и собирает существующие, включая заблокированные в источнике. Redis закрывает вызывающая сторона.

Все гарантии ограничены одним экземпляром сервиса, одним процессом и event loop. При нескольких процессах нужны общие механизмы координации. Перезапуск учебного API сбрасывает источник и создаёт новый namespace. Для итоговой цены заказа и наличия нужен авторитетный источник, а не stale-кэш.

## Собственные тесты для Б+ и выше

Файл [tests/test_additional.py](tests/test_additional.py): восемь функций, девять случаев с учётом параметризации.

- Точная дробная граница TTL cache-aside: равенство времени истечения требует загрузки.
- Свежий SWR не запускает фоновое обновление.
- Точная граница fresh → stale запускает refresh без блокировки ответа.
- Точная граница hard expiry запрещает старый ответ.
- Ошибка DEL одного товара сохраняет cache-hit другого; проверяются нулевые цена и остаток.
- Отмена PATCH во время DEL не позволяет старой версии вернуться.
- Неудачный background refresh не мешает последующему успешному обновлению.
- Холодная загрузка одновременно с PATCH не оставляет старое значение в кэше — в обоих режимах.

Это новые сценарии относительно открытых тестов, а не замена чисел в их копиях. Они используют публичные методы, управляемые часы/события, настоящий Redis и счётчики; формат внутренней записи не зафиксирован тестами.
